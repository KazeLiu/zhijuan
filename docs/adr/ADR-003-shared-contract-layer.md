# ADR-003: 用 `shared/types` + 冻结契约做双人并行开发的解耦面

## 状态
已接受（2026-10-23）

## 背景
首版由两名实现者（后端、前端）在同一仓库、同一时间段并行填充：

- 后端负责 `server/**`：SQLite、会话、场次、资料解析、AI 出题、判分、汇总导出。
- 前端负责 `app/**`：Element Plus 页面、逐题作答、自动保存、管理端表格与表单。

风险有三类：①DTO 字段名双方各写一套，联调时大面积返工；②一方改了接口语义另一方不知情，编译期不报错、运行期才炸；③为了"先跑起来"，用假数据/`as any` 掩盖不一致，最后变成隐性债务。

## 决策
1. 契约先行：`docs/impl-contract.md` 冻结目录归属、33 个接口的路径/入参/出参/错误码、算法（配分、判分、归一化）、前端与后端的硬性要求。
2. 类型即契约：所有跨边界结构定义在 `shared/types/**`（Nuxt 4 原生提供 `#shared` 别名，app 与 server 两侧都能直接 import），由 `shared/types/index.ts` 统一导出。
3. 只允许追加：新增接口/字段可以，改名与改语义必须先在契约 §15 登记再改类型，并在提交信息注明「契约变更」。
4. 文件归属硬切：`server/**` 只归后端、`app/**` 只归前端、`shared/**` 双方可追加、`nuxt.config.ts`/`package.json`/`pnpm-lock.yaml` 等冻结。
5. 禁止假数据：接口未实现时前端只用 loading/empty/error 三态，后端不得返回硬编码示例。

## 备选方案
1. **拆成 `apps/web` + `packages/shared` 的 pnpm workspace**：多一层构建与类型引用配置，对单进程单仓库的首版是纯开销。`#shared` 别名已足够。否。
2. **OpenAPI/Zod 生成类型**：需要额外的 schema 源与生成步骤，两人小团队手工维护一份 TS 类型更快、也更容易读。否（后续若要加接口文档可从此处演进）。
3. **各写各的类型，靠联调对齐**：这正是要避免的返工路径。否。
4. **共享一个「服务层」包给两端调用**：会让客户端可 import 服务端代码，直接违反"客户端不得读库/读 Key"。否。

## 影响
- 变容易：`pnpm typecheck` 能在编译期抓住大部分 DTO 漂移；两人可以真正并行，不必等对方接口就绪；新人按契约 §3 的归属表就知道该改哪里。
- 变难/需注意：
  - `shared/**` 里不能出现 `node:*`、`fs`、`process` 等仅服务端可用的引用（Nuxt 会把它打进客户端图）。
  - 冻结文件意味着"端口被占"这类环境问题需要回到骨架所有者处理，而不是各自改配置。
  - 契约本身要维护：任何语义变更都必须回写 §15，否则契约会逐渐失真 —— 这是接受的成本。
- 可逆性：若项目长大到需要独立部署，`shared/types` 可原样搬成 workspace 包，契约文档随之为其 README；当前结构不阻碍这一步。
